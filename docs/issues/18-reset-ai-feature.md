## 1. 문제

### 증상

- 채널 화면의 `AI 초대`, `내 AI 참여 중`, `응답 가능`, `실행기 오프라인`은 봇 신원, 연결 방식, 실행 상태를 한곳에 섞어 표시한다.
- AI 관리 화면의 `참여 중`은 서버의 에이전트 참여 권한을 뜻하지만, 사용자가 현재 대화 중인 Codex 세션이 그 방에 연결됐다는 뜻은 아니다.
- 실제 확인에서 Deuce 화면에는 `대욱봇`이 방에 참여 중으로 표시됐지만, 현재 `대욱봇` MCP 연결은 `앱 테스트` 채널만 조회했다. 다른 Codex 연결은 `듀스 요구사항` 채널만 조회했다.
- 다른 참여자가 AI와 대화하려면 `AI에게 요청` 또는 AI 멘션을 사용해야 하지만, 어느 실행기·세션이 답하는지 화면에서 판단하기 어렵다.

### 재현 조건

- 환경: 운영 Deuce 웹·데스크톱 0.2.3, Codex의 복수 Deuce MCP 연결
- 단계:
  1. 채널에서 AI를 초대한다.
  2. `AI 관리`에서 여러 AI의 `참여 중` 상태를 확인한다.
  3. 현재 Codex 세션에서 연결별 `list_conversations`를 호출한다.
  4. 화면의 참여 표시와 현재 세션의 접근 가능한 방이 같은지 비교한다.

### 관찰 증거

- 제거 기준 테스트 RED: `ai-retirement-routes.test.ts` 2개 실패. `/api/agents`가 제거된 경로(404)가 아닌 인증 경로(401)로 살아 있고, `/agent-runner`도 `Invalid namespace` 대신 기존 인증 오류를 반환한다.
- 기존 배포 변경은 `fa09a5e`, `2e893e0`, `96a5d6f`로 보존하고 `feat/18-reset-ai-feature`에서 작업한다.

- 사용자 제공 화면: 채널에는 `내 AI (DDD) · 응답 가능 / 대욱봇 (DDD) · 실행기 오프라인` 표시
- 사용자 제공 화면: AI 관리에는 `내 AI`, `대욱봇`이 `DDD이 연결 · 참여 중`, `내 Claude`는 `참여 안 함`으로 표시
- 도구 조회: `대욱봇` 연결은 `앱 테스트`, 별도 요구사항 연결은 `듀스 요구사항`만 반환

### 제거 기준

- 앱에서 AI 등록·초대·해제·요청·실행 상태 UI를 제거한다.
- 데스크톱의 로컬 AI 실행기 연결·복구·키 저장 경로를 제거한다.
- 서버의 새 AI 실행 요청과 자동 멘션 실행 경로를 차단한다.
- 새 설계가 확정되기 전에는 AI 기능이 사용 가능한 것처럼 노출되지 않아야 한다.
- 기존 사람 대화, 멘션, 파일, 반응, 검색, 활동, 알림, 데스크톱 배지는 유지한다.
- 기존 AI 작성 메시지와 운영 데이터는 삭제하지 않고 읽기 가능한 기록으로 보존한다.

## 2. 원인 분석

### 확인된 구조

| 층 | 현재 책임 | 혼동의 원인 |
|---|---|---|
| 웹 | 에이전트 등록·범위·초대·요청·상태 표시 | 봇 신원, 방 참여, PC 실행 상태를 한 흐름에서 표현 |
| 데스크톱 | Codex/Claude CLI 실행기 연결, 암호화 저장, 재실행 복구 | 앱에 연결된 실행기와 사용자가 보고 있는 AI 세션이 별개 |
| 서버 | AI 권한, 방별 grant/exclusion, 실행 요청·영수증, 자동 멘션 실행 | 참여 권한과 실제 응답 가능한 세션을 다른 상태로 관리 |
| MCP | 연결 키별 대화 접근·읽기·게시 | 같은 이름의 봇도 연결 키마다 접근 범위가 다름 |
| DB | AI 사용자·연결·방 권한·실행 기록 | UI가 이 여러 상태를 `참여 중`으로 압축 |

### 근본 원인

현재 구현은 `AgentConnection`을 봇 신원, 권한 주체, MCP 자격증명, PC 실행기 대상으로 함께 사용한다. 서버의 `participating`과 `runtime`은 서로 다른 상태지만 웹은 이를 한 줄에 나란히 보여준다. 현재 Codex 대화 세션 ID는 어떤 모델에도 저장하지 않으므로 “지금 대화 중인 AI가 이 방에 들어왔다”는 계약을 제공할 수 없다.

## 3. Best Practice 조사

기존 의존성의 제거 동작을 사용한다. 새 인증 차단기·큐·상태 동기화 구현은 추가하지 않는다.

- [Fastify 서버](https://fastify.dev/docs/latest/Reference/Server/#setnotfoundhandler): AI 라우트 등록을 없애 기존 not-found 경로로 처리한다. SPA fallback도 API/MCP에는 적용되지 않는다.
- [Socket.IO 네임스페이스](https://socket.io/docs/v4/namespaces/): 실행기 네임스페이스 등록을 제거하고 기존 채팅 네임스페이스만 유지한다. 실제 구버전 소켓 접속 거부를 테스트한다.
- [Prisma migration 수정](https://www.prisma.io/docs/orm/prisma-migrate/workflows/customizing-migrations): 기존 migration을 수정하지 않고, 새 migration에서 키 회수·진행 중 기록 종료만 수행한다. 테이블·메시지는 삭제하지 않는다.

새 제품 계획에서 결정할 항목:

- 사용자에게 보이는 봇 신원과 실제 실행 세션의 분리
- 채널 참여 권한, 온라인 상태, 대화 세션 연결 상태의 독립 표현
- 기존 세션을 채널에 공유할 때의 소유권·가시성·해제 계약
- 과거 AI 메시지·연결 데이터를 보존하는 기능 철회 방식
- 앱에서 비활성화한 API·MCP 자격증명의 서버 차단과 회수 방식

### 엣지 케이스 / 위험 요소

| 시나리오 | 위험도 | 대응 원칙 |
|---|---|---|
| 기존 키로 제거 후에도 API/MCP 접근 | 높음 | UI 제거와 함께 서버 실행·접근 경로를 명시적으로 차단 |
| 진행 중인 AI 요청 | 높음 | 제거 배포 전에 실패 상태로 정리하고 새 요청을 받지 않음 |
| 과거 AI 메시지 삭제 | 높음 | 메시지와 작성자 신원은 기록으로 보존 |
| 운영 DB에서 테이블 즉시 삭제 | 높음 | 이번 제거에서 데이터 파괴 migration을 만들지 않음 |
| 사람 멘션 회귀 | 중간 | AI 전용 분기를 제거하되 일반 멘션 선택·알림은 유지 |
| 구버전 데스크톱 실행기의 재접속 | 높음 | 서버에서 구버전 실행기와 키를 거부 |

## 4. 수정 내용

- 웹: AI 초대·설정·요청·상태 UI와 조회 제거, 사람만 멘션 후보로 표시. 과거 답변·작성자 AI 표시는 유지.
- 서버: AI 관리·요청·MCP 라우트와 실행기 namespace 등록 및 구현 제거. 메시지 작성의 AI 실행 분기를 제거하고 사람 멘션만 검증.
- 데스크톱: 연결 IPC·CLI 실행·암호화 키 저장/복구 제거. 로그인·포커스·읽음 배지·업데이트 유지.
- 패키지: MCP·agent-runner 워크스페이스, 전용 테스트·검증 스크립트·의존성·CI job 제거, lockfile 갱신.
- DB: `20260911080000_retire_ai_feature`에서 키 회수·기본 AI 비움·진행 중 실행 실패 처리. 테이블 및 과거 migration 보존.
- 새 구현은 하지 않고 [사용 흐름 재설계 계획](../design/2026-09-11-ai-restart-plan.md)과 [ADR 013](../adr/013-retire-ai-and-replan.md)을 작성.

## 5. 검증 결과

### 로컬·운영 검증 완료

- `pnpm test`: 244개 통과 (웹 155·서버 79·데스크톱 10). 제거된 기능 테스트는 삭제하고 철회 계약·액션 바 회귀 테스트 추가.
- `pnpm typecheck`, `pnpm build`: 통과.
- `db:migrate:test`: 임시 PostgreSQL에서 기존 8개에 새 migration 적용, 총 9개 성공.
- `ai-retirement-routes`: 구 API/MCP 404, 실제 Socket.IO 구 실행기 접속은 Invalid namespace, health 정상.
- `ai-retirement-data`: 과거 답변·인용·시스템 메시지·권한·완료 기록 보존, 키 회수와 진행 중 종료, 반복 적용 안정성, 사람 멘션·활동 생성 및 AI 멘션 거부 검증.
- 웹 회귀: AI 진입점·후보·조회 제거 및 과거 AI 답변 표시. 데스크톱 preload는 focus/setUnreadCount만 노출.
- 운영 복제 DB에 migration을 먼저 검증한 뒤 백업·구 서버 정지·운영 migration·새 서버 기동 순으로 적용. 연결 7개와 메시지 95개는 유지되고 활성 연결 7개와 기본 AI 1개는 0개가 됨.
- 웹 `20260911-02`와 데스크톱 `0.2.4` 배포. 공개 파일 58개 전체 해시, HTTP 8개, Mac 두 아키텍처 서명·공증·staple·Gatekeeper·DMG를 확인.
- 설치 Mac에서 0.2.3→0.2.4 업데이트·재실행 후 AI 제어가 없는 화면과 메시지 액션 바 비겹침을 확인. 처음 보인 구 AI 제어는 실행 중인 0.2.3 렌더러가 보관한 화면이었고 실제 메뉴 새로고침으로 제거됨.
- 세부 영수증과 복구 경계는 [0.2.4 배포 기록](../handoff/2026-09-11-ai-retirement-release.md)과 [업그레이드 절차](../self-hosting.md#ai-기능-제거-버전으로-업그레이드-18)에 기록.
