# 첫 메시지 버티컬 슬라이스

## 목표

버린 뒤 다시 만드는 화면 프로토타입이 아니라 이후 기능을 계속 얹을 수 있는 최소
워킹 스켈레톤을 만든다. 첫 단계는 Windows PC 한 대에서 두 클라이언트를 실행해 다음
경로를 관통하는 것이다.

```text
Windows 클라이언트 A
  → 메시지 전송
  → TypeScript 서버
  → PostgreSQL 저장
  → 실시간 이벤트 발행
  → Windows 클라이언트 B 즉시 표시
  → 재접속 시 마지막 수신 위치 이후 메시지 복구
```

## 현재 작업 범위

- Flutter 공통 프로젝트와 Windows Runner
- TypeScript 메시지 서버
- PostgreSQL 영구 저장
- 단일 워크스페이스와 단일 채널
- 짧은 텍스트 메시지 전송과 조회
- 서버 저장 후 실시간 전파
- 마지막 서버 순번 이후의 누락 메시지 조회
- 두 Windows 앱 인스턴스를 이용한 관통 검증

## 제외 범위

- 실제 사용자 인증과 운영 권한
- 맥미니 외부 공개와 배포
- Android와 iPhone 빌드
- Cloudflare R2 파일 공유
- 스레드, 검색, 반응과 읽지 않음 표시
- 푸시 알림
- 에이전트 연결
- Teams와 Slack 수준의 시각 완성도

실제 인증이 없으므로 서버는 개발 환경에만 바인딩하고 공개 인터넷에 노출하지 않는다.
개발 사용자 식별자는 테스트 fixture로만 사용하며 운영 인증으로 확장하지 않는다.

## 최소 메시지 계약

서버가 확정하는 메시지는 다음 의미를 갖는다. 구체적인 직렬화와 이벤트 형식은
[메시지 계약 v1](../contracts/messages-v1.md)로 고정한다.

| 필드 | 의미 |
|---|---|
| 메시지 ID | 메시지의 영구 식별자 |
| 클라이언트 메시지 ID | 재전송 시 중복 저장을 막는 요청 식별자 |
| 서버 순번 | 채널 내 표시 순서와 누락 복구 기준 |
| 채널 ID | 메시지가 속한 채널 |
| 작성자 ID | 개발 fixture 사용자 |
| 본문 | 짧은 일반 텍스트 |
| 생성 시각 | 서버가 기록한 시각 |

서버는 DB 저장이 성공한 메시지만 실시간으로 발행한다. 클라이언트는 연결이 복구되면
마지막으로 처리한 서버 순번을 보내고 그 이후의 메시지를 조회한다. 실시간 이벤트와
복구 조회가 같은 메시지 계약을 사용해야 한다.

## 완료 기준

- 두 Windows 앱에서 서로 다른 개발 사용자로 같은 채널에 접속할 수 있다.
- 한 앱이 보낸 메시지가 DB에 한 번 저장되고 두 앱에 같은 ID와 순번으로 표시된다.
- 클라이언트 연결을 끊은 동안 보낸 메시지가 재접속 후 복구된다.
- 같은 클라이언트 메시지 ID가 재전송되어도 DB에 중복 메시지가 생기지 않는다.
- 서버를 재시작해도 기존 메시지가 유지되고 이후 순번이 이어진다.
- 서버·클라이언트 단위 테스트와 Windows 빌드가 통과한다.
