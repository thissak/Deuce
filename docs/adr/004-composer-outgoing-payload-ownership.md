# ADR 004: 컴포저 전송 payload 소유권 — 단일 outgoing mutation과 미해결 실패 중 전송 차단

- 상태: Accepted (2026-09-05)

## 맥락

컴포저는 전송 성공 시 `setText('')`로 입력창을 비웠다. 실 브라우저 검증에서 Enter 직후
이어 쓴 글이 응답 완료 시점에 함께 지워지는 입력 소실이 재현됐다(시드 입력 10건 중
1건만 전송). 1차 수정(전송 즉시 비움 + 실패 시 조건부 복원)과 2차 수정(별도 실패
슬롯·textRef·재전송)은 Codex 독립 검수에서 각각 새 결함을 냈다 — 실패 원문 유실,
업로드 성공 시 초안 삭제, 다음 실패가 앞 실패를 덮어씀, 재전송 시 답장 대상 변경,
재전송 성공이 새 초안의 파일 삭제. 같은 영역에서 검수 2회 연속 새 결함이 나와
글로벌 Fix-Loop Circuit Breaker에 따라 코드 추가를 멈추고 상태 소유권을 재검토했다.

원인은 하나였다. 실패한 요청과 현재 초안이 `text`·`file`·`replyTo`와 실패 슬롯을
공유했고, 새 전송을 허용하면서 슬롯은 하나뿐이었다.

## 결정

1. **초안은 제출 전까지 사용자 소유다.** 제출 시 `Outgoing { body, file, replyToId,
   mentions }`를 스냅샷으로 확정해 초안에서 떼어내고, 초안(텍스트·파일 칩·답장 칩)을
   즉시 비운다. JSON 요청에 필요한 값은 이때 모두 확정하며 재전송도 같은 payload를 보낸다.
2. **요청 중/실패 payload는 단일 `useMutation`(outgoing)이 소유한다.** 텍스트 전송과
   첨부 업로드를 한 mutation으로 묶고(mutationFn 내부에서 JSON/multipart 분기),
   TanStack Query가 이미 제공하는 `variables`·`isPending`·`isError`·`reset()`을
   그대로 쓴다. 별도 실패 슬롯·ref·큐를 두지 않는다.
3. **미해결 payload(요청 중 또는 실패)가 있으면 새 전송을 받지 않는다.** 보내기 버튼을
   비활성화하고 Enter를 무시하되 초안 작성·파일 선택·답장 선택은 계속 허용한다.
   한 번에 payload 하나만 다루므로 덮어쓰기가 구조적으로 불가능하다.
4. **성공·실패 콜백은 초안을 건드리지 않는다.** 성공은 메시지 캐시 갱신(첨부면 공유
   목록 무효화)만 한다. 실패는 안내 바에 원문(파일명 포함)을 보여 「재전송」(동일
   payload)과 「버리기」(`reset()`)만 제공한다. 실패 시 입력창 복원 계약은 payload
   보관 + 명시적 재전송으로 바뀐다.
5. 업로드 중 파일 선택·드롭 차단은 성공 콜백의 초기화로 새 파일이 사라지는 것을 막기
   위한 것이었으므로 4에 따라 제거한다.

## 결과

- 입력 소실·덮어쓰기·답장 대상 변경·새 초안 파일 삭제가 모두 구조적으로 사라졌다.
  Codex 독립 재현 5개와 회귀 테스트 7개가 이를 고정한다.
- 실패한 본문은 입력창에서 편집해 재시도할 수 없다. 편집이 필요하면 버리고 다시
  쓴다(4000자 초과는 textarea maxLength로 이미 차단돼 편집 필요 실패는 드물다).
- 실패가 해소되기 전에는 다른 메시지를 보낼 수 없다. Teams처럼 타임라인에 실패
  메시지를 쌓는 방식은 낙관적 UI 작업으로 미룬다.
- 실패 경로는 단위 테스트로만 검증했다. 실 브라우저 실패 주입은 하지 않았다.
